# General Agent Guidelines

## Rule vocabulary

| Label | Meaning |
| --- | --- |
| **FIRM** | Must follow. Escalate or stop if you cannot. |
| **GUIDELINE** | Default. Override only with clear reason. |
| **MAY** | Optional. |

Unlabeled: treat security, git push/secrets, and SSH as **FIRM**. Treat process and style as **GUIDELINE**.

## Clarity (FIRM)

Aim for about 90% confidence the next agent or human acts correctly. Do not shave tokens into ambiguity. Put the specifics in the brief. Do not read the whole handbook to manufacture them.

Agent-to-agent text (plan Session, spawn notes, `priority.md`) is functionally detailed and succinct. No transcript dumps.

`AGENTS.md` is a routing index. Full rules live under `agents/`. Open a file when its trigger matches.

## The handbook (FIRM)

`agents/` is the agent handbook. In prose, say **handbook**, not "the agents folder."

Ownership is declared in the file, not by filename case. Filenames are lowercase except names an external standard requires (`README.md`, `AGENTS.md`).

There is no living design changelog. The target is `agents/architecture.md`. Open conflicts and leftovers live in `agents/conflicts.md`. Retired rows live in `agents/conflicts-resolved.md` and are not rules. Code that lags the handbook is a plan. Git history and archived plans are the trail.

Do not recreate `HANDOFF.md`, `PRIORITY.md`, `design.md`, or `agents/design/CHANGELOG.md` as living law.

### Who edits what

These change only with **explicit permission in the current message**. Propose and wait:

| File | Role |
| --- | --- |
| Repo-root `README.md` | Install and usage only |
| `agents/human.md` | Who the human is. Not product law |
| `agents/README.md` | How this handbook is run |
| `agents/project.md` | What the project is |
| `agents/architecture.md` | How it is built and how it runs |
| `agents/acceptance.md` | Product checks |
| `agents/general.md`, `documentation.md`, `testing.md` | Project maps. Each amends the matching catalog file and wins on conflict |

A project may name another human-owned file. That file states its own permission. Architecture permission is not enough to edit it.

Agents update these as ordinary work:

| File | Role |
| --- | --- |
| `agents/glossary.md` | Words |
| `agents/priority.md` | Ordered list of plans |
| `agents/conflicts.md` | Active conflicts, and leftovers |
| `agents/conflicts-resolved.md` | Retired rows only. Not rules. Do not delete the file or the section "These rows are not rules" |
| Plan current note | One short note when the next agent would otherwise guess. Overwrite. Not a log |
| `agents/ideas/` | Parked ideas |

Plans are shared. Goal, acceptance, and approach are for a human. A current note is for the next agent, and only when they would otherwise guess.

Root `AGENTS.md` is generated by `agents build`. Do not edit it by hand. Do not gitignore it.

`agents/installed/*` is this catalog. Only `agents install` / `agents update` write it.

A project delta is `agents/<same-path>` (extension; wins over the catalog file) or `agents/<stem>.extend.md`. `agents/<stem>.override.md` replaces that id. Rare. Exactly one of the three forms per id. `agents update` errors if they are mixed. Do not keep a second full copy of a catalog file under `agents/`.

On conflict, handbook files win over `agents/installed/`.

The hard kernel inlined at the top of `AGENTS.md` comes from catalog `always.md`. It points at `security.md`, `git.md`, and the rest. Open those when the domain matches.

After install or update: `agents build`.

## One home per fact (FIRM)

A rule lives in one file. Other files link. They do not restate it.

| Fact | Home |
| --- | --- |
| What the product is | `agents/project.md` |
| How it is built | `agents/architecture.md` |
| Product checks | `agents/acceptance.md` |
| Words | `agents/glossary.md` |
| How we test | project `testing.md`, else this catalog `testing.md` |
| Where writing lives | project `documentation.md`, else this catalog `documentation.md` |
| What to do next | `agents/priority.md` |
| Open conflicts and leftovers | `agents/conflicts.md` |
| Retired conflict rows | `agents/conflicts-resolved.md` |
| How conflicts work | This file, Conflicts |
| This piece of work | one file under `agents/plans/` |
| Bugs | `agents/issues.md` when that file exists |

`architecture.md` is the guide of what has worked and what has failed. It is not a snapshot of today's tree, and it is not a log. When code lags, close the gap with a plan. Do not edit the guide to match leftovers. If the guide looks directionally wrong, stop and meet.

## What is stone (FIRM)

Stone is the current guide. It is not a history, and it is not a ban on a better design.

Architecture records what has worked and warns about what has failed. Acceptance records the product checks. A project may name another human-owned file. Write these only when the human says so. When a sentence stops being true, replace it or remove it. Age is not a reason to keep it.

A guide sentence says what is true, who does it, and what it does not cover. When a later agent would undo it the wrong way, add one sentence of why. Do not list rejected alternatives, dates, or incident logs. Bugs go in `issues.md` when that file exists. A sentence two readers can apply differently is not a guide sentence. Rewrite it or ask.

A better design is welcome. Bring it to the orchestrator with the argument. Do not ship around the guide, and do not treat the guide as a veto because it was written earlier. If the guide looks directionally wrong, stop that issue and meet. Do not hide the miss with a second path.

Chat, plan notes, `priority.md` quotes, and slice fences are not stone. A fence binds that slice only. Do not copy it into architecture or priority as a standing veto. Rows in `conflicts-resolved.md` are not rules. Deleting that file, or the section that says so, does not make them rules.

## Conflicts (FIRM)

This section is the one home for how conflicts work. `agents/README.md` repeats only the session-start sentence. Do not write a second procedure elsewhere.

**Active:** two living rules disagree, and a later agent could follow either. Do not implement either side until the human picks. The row blocks only work that depends on it.

**Leftovers:** code or an old name lags a settled rule. The rule stays. A plan closes the gap. A leftover does not block unrelated work.

When two sources disagree, or a leftover name is still taught as law:

1. Add a row to `agents/conflicts.md` in the same turn. Tell the human. Living rules go under **Active**. Code or an old name goes under **Leftovers**.
1. Handbook wins over plans, catalog, and leftovers. If the handbook looks wrong, stop and ask. Do not silently pick.
1. Name the leftover's fix in a plan on `agents/priority.md`. Link an existing plan. Do not open a twin. An Active row gets no implementation plan until the human picks.
1. A scope fence forbids that rename. It does not license new identifiers that teach the leftover word.
1. When the leftover is gone, or the handbook already says how to read it, move the row to `agents/conflicts-resolved.md`. That file is not a log of ordinary decisions. Append only when retiring an Active fight or a Leftover. Do not copy a living rule into the row. Do not leave a closed table in `conflicts.md`.

### Resolved conflicts are not rules

Session-start sentence. `agents/README.md` repeats these words and does not add a second order:

> The rows in `conflicts-resolved.md` are not rules. They are decisions made at particular moments to iteratively shape the actual living rules in architecture and the rest of the handbook. Do not delete that file. Do not delete, weaken, or rewrite the section “These rows are not rules.” Removing that section does not turn the rows into rules. If that section is missing, restore it before any other edit to that file.

Living rules are `architecture.md`, `acceptance.md`, any stricter file the project declares, `glossary.md` for words, and the selected OpSet document. When a resolved row and a living rule disagree, the living rule is what we believe now. Do not rewrite an old row so that it reads as the current rule.

## Human-readable prose (FIRM)

Handbook files, plan goal, acceptance, approach, and Human checklists are for a human who has not memorized the project.

- Full sentences. Name the actor.
- Do not explain the system as a trail of old ids.
- Link only to stable documents. Not chats, review threads, or session scratch.
- Do not treat an old conversation as law.

The first use of a short id in a human-readable file includes the human name: hide-place-show (`D118`). In `priority.md` and plan Session, the id alone is fine if that plan already named the work.

## User questions (FIRM)

Never use the `ask_user_question` tool. If something is truly blocking, ask in normal chat with full context.

A chat answer is for this session. It is not a file. Write it down only when it changes product law and the human says to, or when the current plan's Session would otherwise leave the next agent guessing. Do not open a conflict row, an issues row, or an architecture paragraph to store a conversation.

Do not re-ask or ignore a prior answer. Re-ask only when new context changed the meaning.

## Residue (FIRM)

Before finishing, remove temp paths, debug prints, failed-attempt code, fake fixtures, and live-env residue you added. Delete dead code everywhere it landed.

## Backwards compatibility (GUIDELINE)

During active development, do not preserve compatibility by default. Prefer a clean break unless real users depend on a released surface.

## Architecture over patches (FIRM)

Prefer a structural fix when the failure will recur or band-aids are stacking. A temporary patch only when the human asks for one.

If the real fix is a multi-session rewrite, stop, present options, and wait. Do not start it silently.

When the real fix lands, remove the competing crutch in the same effort when that is safe.

## Canonical APIs (FIRM)

Use the project's existing API for a job. Do not hand-roll a parallel path.

If that API is insufficient, extend it, convert callers, then use it. Hand-roll only when no contract exists yet and extending would be a large unrelated redesign. Say so in the plan. A one-off that works here and bypasses the shared path will drift at the next call site.

## Optional features in dev (FIRM)

While you are working on an optional feature, enable it in the local environment for that session. Note how in the plan Session. Dev-on is not the ship default.

## Plans (FIRM)

All work is a plan. A "task" is a slice inside a plan. There is no second queue at `agents/tasks/`.

`agents/priority.md` lists what to do next. A current note lives on the plan when the next agent would otherwise guess. It is not a log, and it is not a handoff file.

"Plan" in chat is either ordinary English or a file under `agents/plans/`. Never use Grok `/plan` mode (`enter_plan_mode`, session `plan.md`). That scratch is not a handoff.

| Rule | Detail |
| --- | --- |
| Spine | `agents/plans/<plan>.md`. Look there first when someone names the plan |
| In-repo | The only copy stays in this repo's `agents/plans/`. Cross-repo work goes in that repo. Do not leave the only copy under `~/.grok/sessions/` or `/tmp` unless the current message says so |
| Detail | Optional files under `agents/plans/<id>/` |
| Archive | Completed → `plans/archived/completed/`. Abandoned → `plans/archived/abandoned/`. Do not use `plans/<id>/completed/` as the archive of the whole plan |
| Template | `agents/plans/_TEMPLATE.md` |
| Current note | One short note when the next agent would guess. Overwrite. Do not append a log |
| Status | `draft`, `active`, `waiting`, `accepted`, `abandoned` |
| Optional slices | Skip unless the user includes them |
| Human wait | On the plan, and labeled in `priority.md` |

The plan is not a second architecture. When it is accepted, archive it. If some of its checks should apply to all later work, ask to promote them into `acceptance.md`. If a new plan changes shipped behavior or how the system is built, amend `acceptance.md` or `architecture.md` in the same effort, with permission.

`agents/archive/` may hold ship summaries. Do not treat `plans/archived/` as active work unless `priority.md` names it.

## Ideas (FIRM)

Park ideas in `agents/ideas/` with a category: product, architecture, tooling, or needs an architecture meeting. An idea is not a plan until it has a goal and acceptance. After a meeting, clear ideas that are obsolete, decided, or done.

## Completion

A plan is done when its own checks pass and the gestures in `acceptance.md` still hold. Unit tests support that. They do not replace it.

## Human waits

Only work a human must do. Not agent laziness.

Write a **Human** section on the plan, checkboxes, top to bottom. Do not put hunt recipes there. Label it in `priority.md` so the next agent does not start implementing. Other work continues unless that plan is the only active item.

There is no separate blockers directory. Fold leftover `agents/blockers/` onto the owning plan when you touch them.

| Rule | Kind |
| --- | --- |
| Hard only when the agent must not proceed alone | **FIRM** |
| Short steps and `- [ ]` the human can tick while reading | **FIRM** |
| Do prep you can do first. Note it on the plan when the next agent would guess | **FIRM** |
| Never mark a human step done yourself | **FIRM** |
| No fake blockers | **FIRM** |
| One line on why it is human-only | **FIRM** |

## Continue (FIRM)

A prompt of "Continue" means the top-level agent is the orchestrator
and works `agents/priority.md` from the top. The procedure is this
section and the sections below it. It is not in `human.md`. The
human does not restate the slices. The skill that loads this is
`continue`.

Do not stop after a status report. The orchestrator delegates. It
does not take a large implementation itself.

The orchestrator reads `priority.md`, the active plan's goal,
acceptance, and approach, and the architecture sections that plan
links. It does not read the handbook end to end to start.

Each worker gets a brief: the task itself, or the exact path and
heading where the task is written, plus the checks that decide it.
A brief that only says "Continue" or "read the handbook" is not a
brief. A worker reads the brief and the files it names. If the
brief is missing, the worker stops and says so. It does not invent
the task by reading the handbook. A worker stops when the brief is
done. Continue is not copied into the worker's prompt.

Commit each solid slice on the default branch before the next slice
starts. A trivial slice is solid when the edit is done and the
check that can break has been run. A review pair is solid when the
reviewer reports no remaining defect. Do not commit a rejected
slice. The commit includes the `priority.md` update when the order
changed. Push still follows `git.md`.

Finish the plan that is in progress. Do not leave a slice
half-written. When the plan's agent checks pass and no Human wait
remains, archive it under `plans/archived/completed/` and take it
off the active list. Do not tick a Human checkbox. If a Human wait
is all that remains, label it in `priority.md` and continue with
the next plan that is not waiting on the human.

## Orchestrator (FIRM)

The orchestrator guides. It teaches. It learns. It weighs summary
decisions. The legitimacy of a presentation matters more than the
agent's usual work.

The orchestrator reads code only when an argument is specifically
about that code. Otherwise it judges the argument from the
summaries.

It weighs in when a summary conflicts with the brief, the guide, or
another slice. It asks one question or names one defect. When the
summaries agree with the brief and with the other slices, it
accepts them and moves on.

## Review pair (FIRM)

A non-trivial slice is a review pair. One implementer, then one
fresh reviewer. The reviewer starts after the implementer finishes.
They are not a committee, and they do not meet.

The reviewer checks the change against the brief, re-runs the named
check, and reads the domain notes for the files the diff touches.
A review names defects or says that none remain. A confidence
number is not a review.

The reviewer is the overall-work reviewer. A second reviewer, for
one domain, starts only when the first reviewer reports a domain
question they cannot judge, or the brief already names a domain
grievance the slice can hit. Do not start both up front.

A trivial edit does not need a review pair.

Independent slices may run at the same time when they do not write
the same files and one check does not depend on the other. Each
slice is still a review pair, and inside a pair the reviewer waits
for the implementer.

Children do not spawn. Only the orchestrator starts agents.

## Defects (FIRM)

This is the one path for a disagreement. It applies to a review
pair and to a panel. Do not run extra rounds beside it.

A defect is a broken check, a wrong behavior, or a design that
cannot be built as written. A preference with no broken check is a
note.

Present the defect together with the change that remedies it. The
context of the defect is part of that presentation.

Accept the objection as an issue that needs a remedy, unless an
agent specifically disagrees with the objection. The others do not
have to restate it.

When an agent disagrees, the group works that disagreement out.

When they cannot reconcile, the orchestrator weighs in from the
arguments. If that changes opinions, the group continues from
there.

When the orchestrator's argument does not change opinions, the
orchestrator rates each presentation from 0 to 100 and names the
faulty logic and the faulty steps. The score rates the
presentation. It is not a rank of the person, not a vote, and not
a weight. Do not prefer an agent because they were right before,
because they wrote more, or because they sound more certain. The
purpose is instructional. With each pass the group gets better at
arguing from the work.

The group then re-evaluates all of the findings.

When they still cannot conclude, the orchestrator brings the
issue, the arguments, and the scores to the human. The human
decides. Do not open another round after that ask.

## Panel (FIRM)

A panel meets when a milestone is complete, or when the turn is a
check of an architectural design or a plan. A milestone is a plan
whose agent checks now pass. The panel reads that work once,
before the plan is archived. The members are a Senior Architect, a
Senior Developer, and an Abstraction and Modular Design
Specialist. They do not meet on a timer, and they do not meet
after an ordinary slice.

The orchestrator is not a panel member. The panel follows Defects.

## Subagents

A child does not get a looser license to edit human-owned files or
to restate the guide in a side note.

| Rule | Detail |
| --- | --- |
| Who spawns | Only the orchestrator. Children do not spawn |
| Brief | The task, or the path and heading, plus the checks. A "read the handbook" brief is not a brief |
| Default | One implementer, then one reviewer, for a non-trivial slice |
| Domain reviewer | Only when the overall reviewer cannot judge a domain question, or the brief names a grievance the slice can hit |
| Domain notes | `agents/domains/<name>.md` when that file exists. Current grievances, conflicts, and recurring problems. Remove a line that is no longer true. Do not append a log |
| Batching | One agent may take several related slices when one session is cheaper than several handoffs, and the brief lists them |
| Parallel | Independent slices, no shared writes, independent checks. A review pair stays serial |
| Explore | A short read-only look is fine for unfamiliar code. For an ordinary slice, explore and implement in one agent. No repo-wide explore digest |
| Fresh agent | New subagent per assignment. No `resume_from` unless the human asks |
| Read | The brief and the files it names. Not the handbook end to end |
| Tests | The brief names the checks. One test per check, as `testing.md` says. The reviewer says if a named check has no test |
| Branch | `master` unless isolation is required (`git.md`) |
| Handoff | One short current note on the plan when the next agent would otherwise guess. No transcript. No diary of landed slices |
| Budget | Stop starting slices around 300K orchestrator tokens |
| Design flaw | Stop. Talk about the guide. No wrap-up commit |
| Model | Same as the parent unless the user names one |
| Eligible | Required active plans. Not optional work, and not a plan waiting on a human |

With no plan named, read `priority.md` and the first plan it names.

Wrap-up: residue, the current plan note if the next agent would
otherwise guess, docs if the behavior changed, tests, then commit
and push as `git.md` says.
